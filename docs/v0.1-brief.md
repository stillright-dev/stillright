# Stillright v0.1 — project brief (original, in Portuguese)

Kept as the source of truth for scope during v0.1.

---

Você vai construir comigo a v0.1 de um projeto open source chamado **Stillright** (binário `stillright`; tagline: *"Still right when things go wrong."*): um framework que testa se o comportamento real de uma aplicação continua correto quando as coisas dão errado. Ele transforma regras de negócio em **invariantes verificáveis** e as checa sob eventos duplicados, concorrência e ordem trocada.

Público: times comuns de backend (Node, Python, Go, Ruby) com PostgreSQL que recebem webhooks e eventos (pagamentos, assinaturas, pedidos, ERPs). Referência de categoria: o que a Antithesis faz para sistemas distribuídos, só que para aplicações web normais, local e gratuito.

## Princípios (não negociáveis)

1. **Caixa-preta e agnóstico de linguagem.** O stillright fala com a aplicação por HTTP e com o banco por SQL. O usuário não muda uma linha do código da aplicação para usar.
2. **Invariante = SQL que deve retornar zero linhas.** Se retornar linhas, o invariante quebrou e as linhas são a evidência.
3. **Determinístico.** Toda execução tem uma semente (`--seed`). A mesma semente reproduz a mesma sequência de envios.
4. **Falha alto, não inventa.** Se não der para verificar algo (banco fora, app não respondeu, fixture inválida), o resultado é `ERROR` com o motivo, nunca `PASS`.
5. **Saída útil para humano e para máquina:** terminal legível, `report.json` estável (versionado) e `report.html` autocontido.

## Stack

- **Go** (1.23+), binário único `stillright`. Usar a biblioteca padrão sempre que der; dependências permitidas: `pgx/v5` (Postgres), `gopkg.in/yaml.v3`, e uma lib de CLI leve (`spf13/cobra` ou só `flag`). Nada de framework pesado.
- PostgreSQL rodando nativo no meu Mac (sem Docker por enquanto). Docker Compose só como opção no exemplo.
- Testes com `go test ./...`, cobrindo o motor de perturbação, o shrinker e o parser de cenários.

## Formato do cenário (`stillright/*.yaml`, versionado no repositório do usuário)

```yaml
version: 1
name: pagamento-confirmado
target:
  base_url: http://localhost:3000
  database_url: ${DATABASE_URL}
setup:
  sql: fixtures/seed.sql           # opcional, roda antes de cada execução
  reset: truncate                  # truncate | none (truncate = tabelas listadas em reset_tables)
  reset_tables: [assinaturas, pagamentos, emails]
events:
  - id: pago
    request:
      method: POST
      path: /webhooks/pagamento
      headers: { Content-Type: application/json }
      body_file: fixtures/payment_received.json
  - id: estornado
    request:
      method: POST
      path: /webhooks/pagamento
      body_file: fixtures/payment_refunded.json
    after: pago                    # ordem "correta" de negócio (usada pela perturbação de reordenação)
perturb:
  duplicate: 3                     # cada evento enviado até N vezes
  concurrency: 5                   # envios simultâneos
  reorder: true                    # permite violar o "after"
  delay_ms: [0, 250]               # atraso aleatório por envio
runs: 200                          # quantas sequências geradas
invariants:
  - name: uma assinatura ativa por cliente
    sql: |
      SELECT cliente_id, count(*) FROM assinaturas
      WHERE status = 'ativa' GROUP BY 1 HAVING count(*) > 1
  - name: pagamento estornado não deixa assinatura ativa
    sql: |
      SELECT a.id FROM assinaturas a JOIN pagamentos p ON p.assinatura_id = a.id
      WHERE p.status = 'estornado' AND a.status = 'ativa'
effects:                           # opcional na v0.1, ver Marco 4
  - name: no máximo um e-mail de boas-vindas
    assert: count(host == "api.email.local" && path == "/send") <= 1
```

Validar o arquivo com mensagens de erro claras (linha e campo).

## Marcos (entregar e testar um por vez, nesta ordem)

### Marco 1 — Runner básico
- `stillright run <cenario.yaml>`: reset → setup → envia os eventos na ordem declarada, uma vez → checa invariantes.
- Saída no terminal: cada invariante `PASS` / `FAIL` / `ERROR`, com as linhas retornadas quando falhar (no máximo 10, com contagem total).
- Exit code 0 se tudo passou, 1 se algum `FAIL`, 2 se algum `ERROR`.

### Marco 2 — Motor de perturbação determinístico
- Gerar `runs` sequências a partir de `--seed` (padrão: aleatória, sempre impressa).
- Cada sequência é uma lista de "lotes": envios dentro do mesmo lote vão concorrentes (goroutines, disparo sincronizado por barreira), e os lotes são sequenciais.
- Operações: duplicar, enviar concorrente, reordenar (violando `after`) e atrasar.
- Reset do banco entre sequências.
- Parar na primeira sequência que quebra (flag `--keep-going` para continuar e contar).

### Marco 3 — Redução da sequência (shrinking) e reprodução
- Quando uma sequência falha, reduzir até a menor que ainda falha: remover envios, juntar lotes, tirar atrasos. Rodar de novo a cada passo para confirmar.
- Mostrar o resultado assim:
  ```
  FAIL  uma assinatura ativa por cliente
        menor sequência: [pago ‖ pago]   (2 entregas simultâneas)
        evidência: cliente_id=42 count=2
        reproduzir: stillright run stillright/pagamento.yaml --seed 8812 --replay 3
  ```
- `--replay N` executa só a sequência N da semente.

### Marco 4 — Registro de efeitos externos (proxy)
- `stillright` sobe um proxy HTTP local (porta configurável). O usuário roda a app com `HTTP_PROXY`/`HTTPS_PROXY` apontando para ele (documentar; HTTPS via CONNECT só registra host, sem MITM na v0.1).
- O proxy registra método, host, path, corpo (até 64 KB) e responde com stubs configuráveis por host (`200 {}` por padrão), sem chamar a internet de verdade.
- Asserções `effects` com uma mini-linguagem simples (`count(...)` com `==`, `&&`, `<=`, `>=`, `==`). Sem eval de código.

### Marco 5 — Relatórios e CI
- `--report-json report.json` (schema versionado, documentado em `docs/report-schema.md`) e `--report-html report.html` (arquivo único, sem CDN, legível no celular).
- `action.yml` para GitHub Actions: instala o binário, roda os cenários de uma pasta e publica o resumo no job summary.

### Marco 6 — App de exemplo com bugs plantados (é a demo do README)
- `examples/assinaturas/`: app pequena em Node (Express + pg) com um webhook de pagamento que tem **bugs reais e comuns**: sem idempotência (checa e depois insere, sem constraint), corrida entre "pago" e "estornado" e e-mail enviado em duplicidade.
- Cenários que encontram cada bug, e uma branch ou pasta `fixed/` mostrando a correção (constraint única, `INSERT ... ON CONFLICT`, lock ou outbox). O README mostra o antes e o depois.

## Fora da v0.1 (não fazer agora)
Painel web, histórico entre versões, injeção de crash dentro do processo, MITM de HTTPS, suporte a MySQL, Kafka/filas e servidor MCP para agentes de código. Deixe pontos de extensão limpos (interfaces para `Target`, `Store`, `Effects`), sem implementar.

## Estrutura sugerida
```
cmd/stillright/        # main, CLI
internal/scenario/   # parse + validação do YAML
internal/runner/     # execução, reset, envio HTTP
internal/perturb/    # geração determinística de sequências
internal/shrink/     # redução da sequência
internal/invariant/  # execução dos SQL
internal/effects/    # proxy + asserções
internal/report/     # terminal, json, html
examples/assinaturas/
docs/
```
